## 2. 目录与命名

按需建立以下结构；同一业务场景的专用脚本可与场景同目录，避免两套重复实现。

```text
res://
  scenes/       # 主场景、战斗、单位、界面等，按功能分目录
  scripts/      # 跨场景控制器、模型、资源定义和共享逻辑，按模块分目录
  resources/    # FoodDef、EnemyDef、RecipeDef、WaveDef 等配置实例
  assets/       # 原创图像、字体、音效等源资产
  tests/        # 逻辑测试、集成测试或最小复现场景
  tools/        # 开发及验证辅助工具
  doc/          # 全部设定、设计、决策、验收及发布文档
```

- 文件及目录使用 `snake_case`；脚本类型和节点使用 `PascalCase`；函数、变量和信号使用 `snake_case`；常量使用 `UPPER_SNAKE_CASE`。
- 配置 ID 使用稳定的英文 `snake_case`，不得以显示名称、数组下标或节点名称作为存档身份；更改既有 ID 必须说明迁移策略。
- GDScript 使用类型标注（参数、返回值、成员和数据容器），缩进使用 Tab；文件使用 UTF-8 和 LF。注释说明约束和原因，避免复述代码。
- 每个脚本承担清晰职责；优先组合，不为尚不存在的扩展需求建立复杂继承体系。

## 3. 场景与模块边界

| 模块 | 拥有的职责 | 边界要求 |
|---|---|---|
| RunController | 一局流程、阶段转换、胜败协调 | 明确转换条件及重复事件防护；粮仓归零优先判负 |
| BoardController | 格子占用、放置、移动、移除、行内查询 | 统一维护占用关系；失败操作不能扣费或留下半完成单位 |
| CombatController | 攻击、弹体、伤害、效果、死亡、漏怪 | 统一伤害入口与事件结算顺序，避免重复死亡或漏怪结算 |
| WaveDirector | 时间表、敌人生成、随机行和波次完成条件 | 计划生成结束与场上敌人清空同时满足才可完成，包含召唤物 |
| ShopController | 商品、支付、重复卡进度、升星 | 校验余额、限购、刷新次数及满星退出商品池 |
| RecipeSystem | 食谱候选、修正与事件效果 | 效果注册幂等，统一作用于现有和后续单位 |
| SaveService | 局外进度与关间存档 | 处理版本、读取校验及恢复，不直接驱动战斗节点行为 |

- 节点负责场景生命周期和表现，独立模型负责可测试的状态及计算。场景必须说明依赖和释放责任。
- UI 只请求操作、展示状态；是否允许放置、购买、维修等由对应业务模块判断，不能仅依赖按钮禁用。
- 跨模块通过有类型和明确语义的接口或信号协作；记录信号载荷、发送时机和订阅方。避免跨场景深层 `get_node()` 查找。
- Autoload 仅用于具有明确全局生命周期的服务，新增前记录必要性；不得把所有控制器都放入全局单例。
- 场景退出、重开和阶段切换时清理信号连接、计时、弹体及临时效果；复用对象不得携带上一生命周期状态。
- 输入通过 Input Map 命名动作表达，在交互文档中记录绑定、阶段限制和取消行为。

## 4. 数据、时间与随机性

- `FoodDef`、`EnemyDef`、`RecipeDef`、`WaveDef` 使用自定义 `Resource`；配置实例视为只读，单位当前生命、冷却、状态效果等保存在独立运行对象中。
- 费用、伤害、倍率、生成时间表、解锁条件及上限等可调整参数集中配置。文档说明规则与调参依据，资源保存可执行数据；改动时同步二者，避免重复抄录整张数值表。
- 加载配置时校验唯一 ID、引用存在性、必要字段、有效数值范围和候选池。空池、候选不足等回退规则在实现前明确记录，不临时猜测玩法。
- 游戏时间统一控制攻击、生产、状态持续时间和波次生成。选定计时机制后记录到技术设计；禁止 `delta` 和全局倍速重复缩放。
- 暂停期间只允许查看信息和约定的暂停界面操作，不能放置或进行战斗操作；倍速不影响存档等现实时间操作。
- 随机性使用显式种子和可保存状态的随机源。记录生成、商店及食谱的随机源归属和调用顺序；视觉随机不得消耗玩法随机状态。
- 对相同种子与操作序列验证玩法随机结果。不得在未测试的情况下承诺不同平台或引擎版本之间逐帧确定性。
- 伤害、护甲、持续伤害、攻速修正、减速覆盖、死亡及胜败的结算顺序必须有文档和针对性验证。

## 5. 存档与持久化

- 只向 `user://` 写入玩家存档，不向 `res://` 写运行数据。局外进度与局内快照独立存储和校验，局内损坏不得连带清空可读取的解锁进度。
- `RunState` 的必存内容遵循 `TODO.md`；序列化稳定 ID 和基础数据，不保存节点引用或实例 ID。
- 存档包含格式版本；读取时校验字段、范围和引用。版本迁移或拒绝旧版本的行为必须记录，并给予明确提示。
- 仅保存准备阶段状态，包含选谱、购物、调位、维修后的结果及防重复领奖信息。选谱与准备阶段的交界、奖励提交及保存时机必须在状态机设计中明确。
- 开战前保留可恢复的准备快照；战斗中退出后按基线回到该快照。写入采用临时文件后替换等完整性措施，处理写入失败，不把失败显示为成功。
- 存档测试覆盖往返恢复、重复加载、损坏和未知版本；开发调试存档与正常测试数据隔离。

## 6. 验证与验收记录

按修改风险选择验证深度，不为纯文档改动新增游戏测试。正式玩法变更至少覆盖正常流程、边界和重复操作；缺陷修复保留适合自动化的回归用例，或记录可复现的人工步骤。

| 改动类型 | 最低验证要求 |
|---|---|
| 文档 | 引用可达、无规则冲突、状态与仓库实际一致 |
| 脚本／资源／场景 | Godot 导入与解析检查、相关场景运行、无新增丢失引用 |
| 数值和业务逻辑 | 公式、边界、重复触发及受影响的 `TODO.md` 必验项 |
| UI／输入／动画 | 在编辑器或运行窗口检查布局、缩放、交互、取消和暂停状态 |
| 存档／局内流程 | 保存恢复一致、奖励不重复、重开清理、胜败竞争条件 |
| 发布／性能 | 目标设备导出启动、完整流程、压力场景、实际帧率记录 |

引擎可执行文件存在且版本正确时，可在项目根目录运行以下导入检查；命令名按本机实际安装调整：

```sh
godot --version
godot --headless --path . --editor --import
```

主场景建立后可进行有限帧启动冒烟检查：

```sh
godot --headless --path . --quit-after 120
```

以上是待使用的检查方式，并非已执行结果，也不能代替玩法或视觉验收。尚未选定自动化测试框架；如需引入，在技术文档记录版本、执行命令及用途。

验收记录放在 `doc/testing/`，注明日期、提交或工作区版本、Godot 版本、平台、步骤、期望、实际结果及剩余问题。性能以 `TODO.md` 的 40 个美食、100 个敌人及攻击效果为压力条件，记录设备、分辨率和测量方式后才能判断是否达到 60 FPS。

## 7. 版本控制与发布

- 使用小而完整的提交表达单项行为变更；相关设计、数据、实现和验证记录一起交付。避免混入无关重排、场景重存或资源再导入噪声。
- 跟踪源脚本、场景、资源、需要保留的 `.uid`、资源旁的 `.import` 导入配置及非敏感工程配置；不提交 `.godot/` 缓存、运行存档、日志或导出产物。
- 移动和重命名资源优先使用 Godot 编辑器维护引用；无论使用何种方式，完成后检查场景、资源和 UID 引用。
- 导出预设只保存非敏感配置；签名材料、凭据和本机绝对路径不得入库。发布前关闭开发作弊入口并检查资源范围。
- 可分享试玩包须有 `doc/releases/` 说明：版本、引擎与导出模板版本、目标系统、构建步骤、启动方式、存档兼容性、验证结果和已知问题。
- 里程碑按 `TODO.md` 的实际验收推进，时间估算不作为完成证据。
